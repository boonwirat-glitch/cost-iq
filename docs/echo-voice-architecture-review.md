# Echo — ทำไมปัญหา "ฟังไม่รู้เรื่อง" ถึงแก้ไม่จบ

บทวิเคราะห์สถาปัตยกรรม · 2026-08-08 · ไม่มีการแก้โค้ดในรอบนี้
หลักฐานทั้งหมดมาจากโค้ดที่ deploy อยู่จริง (`worker/freshket-sense-ai-proxy-v2.js`,
`src/09_conv_intel.js`), ข้อมูลจริงใน Supabase (135 session) และ git history

---

## คำตอบสั้น

**ไม่ใช่เพราะโมเดล AI** ที่ใช้อยู่นี้เป็นโมเดลระดับเดียวกับที่ทุกเจ้าใช้ทำ voice
summary ได้ปกติ ปัญหาอยู่ที่การออกแบบรอบๆ ตัวโมเดล 3 ชั้น:

1. **เราวัดผลด้วยตัวเลขที่ตีความผิด และตั้งเป้าที่ไม่มีวันถึง** — ทำให้รู้สึกว่า
   "แก้แล้วก็ยังไม่ผ่าน" ทั้งที่ของอาจดีขึ้นจริง
2. **เราทำลายหลักฐานทิ้งทุกครั้ง** — ไฟล์เสียงถูกลบภายในไม่กี่วินาทีหลังถอดเสร็จ
   จึงไม่มีทางรู้ว่าการแก้แต่ละครั้งได้ผลหรือไม่ ทุกการแก้เลยเป็นการเดา
3. **ชิ้นส่วนที่มีโอกาสแก้คำไทยเพี้ยนได้ที่สุด ถูกสั่งห้ามแก้** — และตัวที่ตัดสินใจ
   แทนคนกลับวิ่งบนโมเดลตัวล่างสุดของรายการเกือบทุกครั้ง

ข้อ 2 คือรากที่แท้จริง ตราบใดที่วัดซ้ำไม่ได้ ปัญหานี้จะ "แก้ไม่จบ" ตลอดไป
ไม่ว่าจะเปลี่ยนโมเดลกี่รอบ

## หลักฐาน 7 ข้อ

### 1. ตัววัดพังก่อนระบบพัง

`/eval` เอาค่า `exp(avg_logprob)` มาตั้งชื่อว่า **"thai_accuracy"** แล้วตั้งเป้า
**0.90** (`worker/…-v2.js:751-754`)

ค่านี้ **ไม่ใช่ความถูกต้อง** มันคือความน่าจะเป็นเฉลี่ยต่อ token ที่โมเดลให้กับคำ
ที่ตัวเองเลือก การจะได้ 0.90 แปลว่าต้องมี avg_logprob ≥ −0.105 ซึ่งภาษาพูดจริง
ในร้านอาหาร **ไม่มีทางถึง** ต่อให้ถอดถูกทุกคำ

ข้อมูลจริงใน DB ตอนนี้:

| | ค่า |
|---|---|
| session ที่มีค่านี้ | 9 |
| เฉลี่ย | **0.533** |
| ต่ำสุด – สูงสุด | 0.361 – 0.720 |
| ผ่านเป้า 0.90 | **0 session** |
| แตะ 0.85 ด้วยซ้ำ | **0 session** |

เลข 53% ที่เห็นจึง **ไม่ได้แปลว่าถอดผิด 47%** แต่ถูกติดป้ายว่า "ความแม่นภาษาไทย"
เลยอ่านออกมาเป็นแบบนั้น · เป้าที่ไม่มีวันเขียว = ความรู้สึกว่า "แก้ไม่จบ"

### 2. เราทำลายหลักฐานทิ้งทุกครั้ง ★ ข้อที่สำคัญที่สุด

worker ลบไฟล์เสียงออกจาก storage ทันทีที่ถอดเสร็จ
(`sbStorageDelete` บรรทัด 1117 และ 1130) และ set `audio_path = null`

ผลจริง ณ วันนี้:

| | จำนวน |
|---|---|
| session ทั้งหมด | 135 |
| มี transcript (เคยอัดเสียงจริง) | 44 |
| **ยังมีไฟล์เสียงเก็บไว้** | **1** |

แปลว่า **บทสนทนาจริง 43 คลิปหายไปแล้วถาวร** — เวลาบุชบอกว่า "ฟังไม่รู้เรื่อง"
เราไม่มีทางกลับไปฟังว่าเสียงต้นฉบับเป็นยังไง ไม่มีทางลองโมเดลใหม่กับคลิปเดิม
ไม่มีทางพิสูจน์ว่าการแก้ครั้งนี้ดีกว่าครั้งก่อน

นี่คือเหตุผลเชิงโครงสร้างที่ทำให้ทุกการแก้กลายเป็นการเดา และทำไมมันถึงวนซ้ำ

> เอกสารแผนรอบก่อนของผมเขียนว่า "ไฟล์เสียงจริงเก็บอยู่ใน Supabase storage แล้ว
> สร้างชุดทดสอบได้ทันที" — **ผิด** ตรวจข้อมูลจริงแล้วเหลือแค่ 1 ไฟล์

### 3. ตัวที่ได้ยินเสียงจริง ถูกห้ามแก้คำ

Gemini รับ audio จริงเข้าไปทั้งไฟล์ (`inline_data`, บรรทัด 268) — เป็นชิ้นเดียว
ในระบบที่ "ได้ยิน" นอกจาก Whisper แต่ prompt สั่งไว้ว่า:

> `TRANSCRIPT (ถอดจาก audio เดียวกันนี้ — ห้ามแก้ text ห้ามเพิ่ม/ลบ segment)` (:250)

เราจึงใช้มันแค่ตอบว่า "ใครพูด" ทั้งที่มันมีโอกาสจับคำไทยที่ Whisper เพี้ยนได้
(เหตุผลเดิมที่ห้ามคือกลัว hallucination ซึ่งสมเหตุสมผล — แต่ห้ามทั้งหมดคือ
ทิ้งของฟรี ควรเปิดให้แก้เฉพาะคำที่ Whisper เองบอกว่าไม่มั่นใจ)

### 4. สมองวิ่งบนโมเดลตัวล่างสุดของรายการเกือบทุกครั้ง

`BRAIN_MODEL_CHAIN` (บรรทัด 869) เรียงจากแรงสุดลงมา:

```
gemini-3.5-pro  →  claude-sonnet-5  →  claude-sonnet-4-6  →  gemini-2.5-flash
                                                             ↑ คอมเมนต์ในโค้ด
                                                               เขียนเองว่า
                                                               "absolute floor"
```

ข้อมูลจริงจาก DB:

| โมเดลที่ถูกใช้จริง | ครั้ง |
|---|---|
| gemini-2.5-flash (ตัวล่างสุด) | **17** |
| claude-sonnet-4-6 | 1 |
| 2 ตัวบนสุด | **0** |

โค้ดออกแบบให้ตกชั้น **เงียบๆ** เมื่อเจอ error 4xx (บรรทัด 900-912) ไม่มีใครรู้ว่า
เกิดขึ้น ไม่มีการแจ้งเตือน — เราคิดว่ากำลังใช้โมเดลแรงสุด แต่ความจริงคือตัวถูกสุด
เกือบทุกครั้ง (น่าจะเป็นเพราะชื่อโมเดล 2 ตัวบนไม่มีจริงบน key ที่ใช้อยู่)

### 5. การอัดเสียงไม่ได้ตั้งค่าอะไรเลย

`navigator.mediaDevices.getUserMedia({ audio: true })` (`09_conv_intel.js:1022`)
— ไม่มี constraint สักตัว บวก `audioBitsPerSecond: 24000`

ปล่อยค่า default แปลว่ามือถือจะเปิด echo cancellation / noise suppression /
auto gain control ที่ **จูนมาเพื่อการโทรศัพท์** คือ *คนเดียว ปากใกล้ไมค์ ตัดเสียง
รอบข้างทิ้ง* ซึ่งตรงข้ามกับสถานการณ์จริงของเราเป๊ะ: **วางมือถือบนโต๊ะ 2 คนนั่งคนละ
ฝั่ง ในร้านอาหารที่มีเสียงรบกวน** — noise suppression จะกินเสียงลูกค้าที่อยู่ไกล
ทิ้งไปด้วย ส่วน AGC จะดันเสียงรบกวนขึ้นมาตอนไม่มีใครพูด

### 6. ศัพท์ที่ป้อนให้ Whisper มี 6 คำ

`Freshket, SKU, delivery, order, กิโล, ลัง` (บรรทัด 190) + ชื่อร้านที่กำลังคุยด้วย
(เพิ่มเข้ามารอบ A0 แล้ว ดีขึ้นแล้วส่วนหนึ่ง)

แต่ยังไม่มี **ชื่อสินค้า** สักตัว ทั้งที่ Sense มี catalogue SKU รายร้านอยู่ใน
Supabase (`sense_skus`) และ worker เข้าถึงได้อยู่แล้ว — บทสนทนาขายวัตถุดิบอาหาร
เต็มไปด้วยชื่อของ ชื่อหน่วย ชื่อแบรนด์ ซึ่งเป็นคำที่เพี้ยนบ่อยที่สุดพอดี

ข้อควรระวัง: prompt ของ Whisper มีเพดาน 224 token ถ้ายัดยาวเกินจะถูกตัดหัวทิ้ง
**เงียบๆ** — ตอนนี้ prompt ไทยยาว ~207 ตัวอักษร ใกล้เพดานแล้ว การยัด glossary
ต้องเลือกเฉพาะ SKU ของร้านนั้น ไม่ใช่ยัดทั้ง catalogue

## อะไรแก้ได้ vs อะไรคือข้อจำกัดทางฟิสิกส์

**แก้ได้จริง**

- ตัววัด: เลิกเรียกมันว่า accuracy, เลิกตั้งเป้า 0.90, ใช้เป็นสัญญาณเทียบ
  *ภายในคลิปเดียวกัน* ว่าท่อนไหนน่าสงสัย (รอบนี้ทำไปแล้ว — สมองได้รับธง
  `[ฟังไม่ชัด]` รายท่อนแล้ว)
- เก็บไฟล์เสียงไว้ (อย่างน้อยแบบสุ่มตัวอย่าง หรือเก็บ 30 วันแล้วค่อยลบ)
- ตั้งค่าไมค์ให้ตรงกับสถานการณ์ประชุมโต๊ะ
- ให้ Gemini แก้เฉพาะคำที่ Whisper ไม่มั่นใจ
- glossary SKU รายร้าน
- เลิกตกชั้นโมเดลแบบเงียบ + ตรวจว่าชื่อโมเดล 2 ตัวบนใช้ได้จริงไหม

**ข้อจำกัดทางฟิสิกส์ — ยอมรับ ไม่ต้องไล่แก้**

- มือถือหนึ่งเครื่องวางบนโต๊ะในร้านที่เสียงดัง จะมีบางช่วงที่ฟังไม่ออกเสมอ
  ไม่ว่าโมเดลอะไร คนฟังเองก็ฟังไม่ออก
- คนพูดพร้อมกัน / พูดค้างประโยค / เสียงจากโต๊ะข้าง — ไม่มีระบบไหนกู้ได้
- **ทางที่ถูกคือออกแบบให้ระบบ "รู้ตัวว่าไม่รู้"** แล้วยกเป็นคำถามให้ rep ไปถามใหม่
  ดีกว่าให้มันเดาแล้วเขียนออกมาเนียนๆ ผิดๆ

### ชุดทดสอบที่ไม่ต้องให้คนนั่งพิมพ์เฉลย

ไม่ต้องมี ground truth ก็วัดได้ ใช้การเทียบสัมพัทธ์:

1. **ตัวเลขนิ่งไหม** — รันคลิปเดิม 2 ครั้ง ตัวเลข/ราคา/หน่วยที่ดึงได้ต้องตรงกัน
2. **ชื่อเฉพาะสะกดคงที่ไหม** — ชื่อร้าน/แบรนด์เดียวกันต้องสะกดเหมือนเดิมทุกครั้ง
   (เคสจริง: ชื่อสาขาเดียวถูกถอดเป็น 2 แบบในคลิปเดียวกัน)
3. **สัดส่วนคำที่พจนานุกรมไม่รู้จัก** — ยิ่งเพี้ยนยิ่งเยอะ ไม่ต้องรู้คำที่ถูก
4. **เทียบเวอร์ชัน** — การแก้ครั้งใหม่ทำ 3 ตัวข้างบนดีขึ้นหรือแย่ลง เทียบกับคลิปชุดเดิม

แค่นี้ก็พอตัดสินได้ว่า "ดีขึ้นจริงไหม" โดยไม่ต้องมีใครนั่งถอดเทปเฉลย

## สรุปให้สั้นที่สุด

เราไม่ได้เลือกโมเดลผิด เราสร้างระบบที่ **วัดผลด้วยตัวเลขที่ตีความผิด แล้วลบหลักฐาน
ทิ้งทุกครั้งก่อนจะได้ตรวจ** ทุกการแก้จึงเป็นการเดาที่ไม่มีทางรู้ว่าถูกหรือผิด

เริ่มจากข้อ 1 กับ 2 ก่อน (แรงน้อยมากทั้งคู่) แล้วเรื่องนี้จะเลิกวนทันที
